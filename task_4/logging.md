### данные для логов
#### INFO
- trace_id
- user_id
- order_id
- order_status
- timestamp
- HTTP code

#### DEBUG (only for devs testing)
- на усмотрение разработчиков

#### WARN (для нестандартного поведения, которое не является ошибками, например - неверно ввели пароль или обратились к ендпоинту без прав доступа)
- user_id
- uri
- timestamp
- HTTP code

### ERROR (для ошибок сервера)
- user_id
- timestamp
- uri
- HTTP code
- error code

### мотивация
Логирование в совокупности с трейсингом позволит быстрее и проще находить баги в системе и быстро на них реагировать.
Так же это наглядно покажет порядок действий пользователя, что позволит поддержке более предметно вести дискуссию с клиентом.

Первостепенно логами стоит покрыть пользовательский путь запросов.

### решение
Как решение можно рассмотреть стек OLK - довольно распространённое решение с хорошей документацией. Logstash довольно просто интегрируется с распространёнными системами.
Elasticsearch оснашен быстрым полнотекстовым поиском, что позволит быстро копаться в логах.
Для внедрения необходимо интегрировать Beats'ы в необходимые системы и связать с logstash.

Важно! не отображать в логах персональную инфу!
Доступ организовать разработчикам и тех.поддержке (возможно как-то ограничить доступ)

политика хранения логов:
1. логи разделить по индексам, где каждый индекс соответствует своему сервису
2. для особых случаев можно сделать специальный индекс, где может быть смешение логов с нескольких сервисов
3. хранить логи минимум один квартал (3 месяца), мб не перед удаление складывать их в какое-то долгосрочное хранилище

### превращениt системы сбора логов в систему анализа логов
хорошей практикой будет настроить вывод ошибок в какой нибудь канал связи - email/slack/mattermost
в последствии можно настроить алёртинг средствами logstash/prometheus
